# The web tools — source

This folder is the source. The built single-file versions live in
[`../site/`](../site/), which is what gets published; rebuild them after
changing anything here (see the root README).

A single-page programmer that talks to the radio over Web Serial. No install,
no Python, works on Windows, macOS and Linux from the same files.

```
index.html               the programmer
compare.html             the mapping notebook
th2000-core.js           the shared model, used by both
index.html               the page, needs th2000-core.js beside it
th2000-core.js           framing + codeplug codec, no DOM
DefaulFile.icf           the manufacturer's default codeplug, for a dry run
th2000-core.test.js      193 checks, runs under node
ui.test.js               475 checks, drives the programmer in jsdom
compare.test.js          43 checks, drives the notebook in jsdom
```

**Use `th2000-standalone.html` unless you are working on the code.** It is
generated by inlining `th2000-core.js` into `index.html`, so the two cannot
drift apart, and there is no second file to lose. The two-file layout exists
because a DOM-free core can be unit tested under node.

If you do use `index.html`, `th2000-core.js` must sit in the same folder with
exactly that name. If it is missing the page now says so plainly and disables
the buttons, rather than failing later with "cannot read properties of
undefined".

## Run it

Web Serial needs a **secure context**, so opening `index.html` by
double-clicking will not work — `navigator.serial` is undefined on `file://`.
Serve the folder instead:

```bash
cd web
python3 -m http.server 8000
```

Then open `http://localhost:8000/th2000-standalone.html`.

Then open **http://localhost:8000** in Chrome or Edge on desktop. Firefox and
Safari do not implement Web Serial; the page detects that and tells you, and
file editing still works.

## Try it without a radio

Open the page and press **Open file**, then pick `DefaulFile.icf`. You get the
manufacturer's default codeplug: 200 channels with channel 1 at 435.30000, the
power-on message `UV8800`, band limits 108–174 and 400–480 MHz. Edit a few
channels, **Save .icf**, and open that file in the OEM software. If it displays
your edits correctly, the memory map is right.

The grid also starts empty and editable, so you can build a codeplug from
scratch and save it. Writing to a radio stays disabled until the codeplug came
from a radio or a file — a blank image has no band limits of its own and is not
something you want to push into hardware.

## Then the radio

1. Radio off, cable in, radio on.
2. **Connect** — pick the port in the browser dialog. 57600 8N1, RTS and DTR asserted.
3. **Read radio** — 22 blocks of 512 bytes.
4. **Save .icf** immediately. That file is your way back.
5. Edit, then **Write radio**.

*Verify after write* is on by default: after uploading, the page reads the
codeplug back and compares it byte for byte, so a silently corrupted block gets
caught rather than discovered later on the air.

*Legacy framing* switches to the older frame format used elsewhere in this
radio family. Try it if the handshake fails — the commands are identical, only
the body transform differs.

## The nameplate

Top left, under the model name: **codeplug &middot; 200 ch** before anything is
loaded, then **codeplug &middot; 2 of 200 ch** once a file or a radio has
supplied one. The count follows every edit.

*Codeplug* is the trade term for a radio's entire configuration in one file. The
name is Motorola's, and it was once literal - a module of diodes you plugged in
to define the channels. Hover the nameplate for that note.

## Theme and remembered settings

The **Options** tab has a theme control: Auto, Light or Dark. Auto follows
whatever your system is set to and changes with it. The comparison notebook
reads the same setting, so both tools match.

Remembered on this computer: the theme, the panel width, and the four transfer
options. **Codeplugs are never stored.** A stale one reappearing quietly after a
refresh is exactly how the wrong thing gets written to a radio.

If storage is unavailable - private browsing, a sandboxed viewer, storage turned
off - the page still works, it simply forgets between sessions.

## Working with channels

**CSV import and export.** Export writes every channel field as a spreadsheet
file; import reads one back. The importer is deliberately tolerant - columns in
any order, optional columns omitted, and a header matcher that accepts
variations, so a hand-written `name,rx freq,TX,Tone` works as well as the exact
export format. Quoted fields containing commas are handled.

Import is **all-or-nothing**. If any row has a problem nothing is applied, and
you get a list of faults with the line number of each. A half-imported channel
list is worse than none. You also choose whether channels not mentioned in the
file are left alone or cleared first.

This is the feature that makes the tool worth using over the manufacturer's:
paste from a repeater database, sort, fill down, use formulas for offsets, keep
your channel list in version control.

**Bulk operations**, on the Bulk tab: apply any field across a range of
channels, find-and-replace in names, copy, move or delete a range, and close
gaps so channels run without holes. Ranges are inclusive and use the numbers
shown in the table.

**Checks**, on the Check tab: out-of-band transmit as an error, out-of-band
receive as a warning, duplicate channels, frequencies that do not sit on their
own tuning step, and names containing characters the radio may not display.

**FM broadcast presets** and the FM VFO are editable on the Radio tab. The
per-preset enable bits are inferred from a factory image rather than confirmed,
and are labelled as such.

**Print** produces a plain channel sheet for the glovebox.

## Editing in the table

**Double-click any cell** to edit it where it sits. The editable columns are the
ones the table already shows: name, receive, transmit, encode, decode, power,
bandwidth, step and scan. The channel number and the derived Shift column are
not editable, and neither is anything the table does not display - those stay in
the side panel, which remains the complete view.

* **Enter** commits and drops to the same column one row down, which is the
  quick way to type a column of frequencies.
* **Tab** commits and moves to the next editable column, wrapping to the next
  row. Shift+Tab goes back.
* **Escape** abandons that cell and leaves the value alone.
* Clicking away commits.

The grid uses a fixed column layout with declared widths, so opening an editor
never moves anything. It also has a minimum width: on a narrow window or a
phone the table scrolls sideways rather than squeezing every column into
something unreadable. Without that, a cell holding a 260-option tone picker
would widen its column and shove every other one sideways.

Encode and decode use the same 260-value picker as the side panel; power,
bandwidth, step and scan are dropdowns; name and the frequencies are text. A
frequency that cannot be read is refused, the cell turns red and the editor
stays open with what you typed.

**An empty slot is shown as empty.** On a real radio every unused channel still
holds whatever the factory left in it - on this one, 435.00000 with a 10 kHz
step - so an untouched slot would otherwise look like a real channel and
claiming it would inherit those leftovers. Unused slots present blank, and
claiming one starts from a clean channel. Bits nobody has mapped are carried
through untouched either way.

With a channel selected and no field focused:

| Key | Does |
|---|---|
| **Ctrl+C** | copy the channel |
| **Ctrl+X** | cut it - copies, then empties the row |
| **Ctrl+V** | paste it into the selected row |
| **Delete** | clear the selected channel |
| **Up / Down** | move the selection |

These work on any keyboard layout. The shortcuts match either the character or
the physical key, so a Cyrillic layout - where Ctrl+C arrives as
&#1089; rather than c - works, and so does Dvorak, where the letter is right but
sits somewhere else.

The clipboard lives in the page, so a paste always puts back exactly the channel
that was copied. The copy is also offered to the system clipboard as a CSV row,
for pasting into a spreadsheet, but that is a convenience and never required.
Shortcuts stand aside while a field has focus, while a dialogue is open, and
when you have text selected to copy.

**Copy to next** duplicates the selected channel into the slot below and
selects the copy. It refuses politely if the source is empty.

Each row that holds a channel ends with an **&times;** that clears it. There is
no confirmation, matching the *Clear channel* button beside it: this only edits
the codeplug in front of you, it shows up under *View changes*, and nothing
reaches the radio until you write. Empty rows have no control, so there is
nothing to misclick.

A transmit frequency shows as **off** when the channel is receive-only and
**not set** when nothing has been entered yet. Both are stored differently and
both mean the radio will not transmit.

**Any column can start an empty channel off** - type a name, pick a power level,
whatever suits. The first edit claims the slot. If it still has no receive
frequency the table says *not set* rather than showing 0.00000, the status line
mentions it, and the checks flag it as an error before any write.

The grid and the side panel are two views of the same channel and stay in step
in both directions.

## Seeing what changes before it happens

**Compare with…** loads a second codeplug and shows what differs in the terms
you edit in, not just as bytes.

Every dialogue that shows differences opens with a centred **direction line**,
so the arrows in the rows below it are unambiguous:

| Dialogue | Reads |
|---|---|
| Compare with&hellip; | `DefaulFile.icf` &rarr; `Current state` |
| View changes | `As loaded` &rarr; `Current state` |
| Before writing | `On the radio now` &rarr; `After this write` |

Read `Squelch level 5 -> OFF` against the first and it says the file had 5 and
yours has OFF.

Then the changes, then the byte tally.

**The browser tab** carries the open file's name &mdash;
`ORIGIN_BACKUP_ConFile.icf — TH-2000 codeplug` &mdash; with a leading dot while
there are unsaved changes. A radio read shows *Read from radio*.

* **channels** added, changed or removed, naming each field that moved
  (`receive 435.00000 MHz -> 435.10000 MHz`)
* **radio settings** by name and value (`Backlight 7 -> 3`,
  `P1 short KEY-Low -> Frequency Reverse`), including the password, the intro
  lines and the band limits
* **FM broadcast** presets and the VFO
* **unused channel slots** whose bytes moved. The radio ignores them, since the
  in-use list decides what exists, but they are real bytes and are counted, so
  the summary can always account for its own total
* the **byte level** underneath, folded away, for anything not yet mapped

The byte table is collapsed by default in every dialogue that offers it, and
comes in two layers:

* **Byte level — N non-channel bytes** opens a table of settings, band limits,
  tone blocks and the unmapped areas. Channel bytes are left out, because
  editing a single channel moves about twenty of them and importing a CSV moves
  thousands, which would bury everything else. Every byte still waiting to be
  mapped lives outside the channel area, so this is the view that matters when
  working one out.
* **Show all N bytes, channels included** opens the complete table underneath.

Each label counts exactly what its own table contains.

Once you edit anything, a **View changes** button appears beside the unsaved
marker in the status bar. It shows the same decoded comparison against the
codeplug as it was read or opened, so you can see what you have done before
saving or writing.

The same engine runs automatically before a write. **Compare before write** is
on by default: the tool reads the radio fresh, diffs it against what you are
about to send, and shows that alongside the validation results before anything
leaves the computer. If nothing differs it says so and sends nothing. Cancelling
is safe.

This turns a write from an act of faith into a reviewable change, which is the
single best answer to "how do I know this will not wreck my radio".

Two consequences worth knowing. A write now runs **three** serial sessions -
read to compare, write, read to verify - so it takes about three times as long
as before. And an unchanged codeplug will not be written at all, which is
deliberate: there is no reason to send bytes that are already there.

**Auto-backup on read** is also on by default. Every successful read quietly
saves a timestamped `.icf` before you touch anything.

## th2000-compare.html - the mapping notebook

A separate single-file tool for one job: working out what the unmapped bytes
mean, and keeping a record of it.

Drop your original backup on the **left**. It is the baseline and is never
written to - the tool only ever reads. Drop the file you saved after changing
one setting on the **right**. The table underneath shows every byte that
differs, with binary before and after, which bits moved, and the value those
bits hold.

Then type what you changed - "Squelch level 0 to 3" - and press **Record**.
That pairs your description with the bytes and adds it to a running log.

**Right &rarr; baseline** promotes the right-hand file to the left so you can
change the next setting without reloading anything. Change, save, drop,
describe, record, promote. About a minute per field.

**Export log** writes a text file with every observation: the description, both
filenames, a timestamp, the byte table, and a JSON block at the end. That file
is what to send back.

Two things worth knowing:

* **Bits shows what moved, not the field width.** Changing a value from 0 to 3
  in a three-bit field only moves two bits. Record the same setting at two or
  three values and the real width becomes obvious.
* **The log lives in the page only.** There is no storage behind it, so export
  before closing the tab. The page will warn you if you try to leave with
  unexported observations.

## The VFOs

Ten more channel records sit between the channel array and the name table, at
`0x1068`-`0x1140`. Nothing had mapped that region until a radio was read with
known VFO settings; slots **204-209** turned out to be the two VFOs, one slot
per band.

The **VFO A/B** tab splits into **VFO A (left)** and **VFO B (right)**, matching the
manufacturer's own window, with VHF and UHF under each. The fields are the ones
that window offers - frequency, encode, decode, power, wide, step, signal,
busy lock, scramble, DTMF PTT-ID, **Rev** and **Talk Off** - and each has its
own Apply. Hover any field for what it does. Only the
record you apply is written.

Each VFO also has a 220 MHz slot, inherited from a tri-band sibling. This radio
has no such band, so those two are not shown and never written.

VFOs are not in the in-use bitmap and have no entry in the name table, so
neither is touched.

## Radio settings

The Radio tab has 29 settings: squelch, time-out timer, auto power off,
backlight, LED mode, display mode, scan type, key mode and lock, beep, dual
watch, monitor, squelch tail, and all ten programmable key assignments.

**Every one was confirmed by measurement**, not by reading decompiled code. The
procedure was: change one setting in the manufacturer's software, save, diff the
bytes, repeat - 59 observations in all. Bit positions and widths come from those
bytes; option labels come from the literal string tables in the CPS, and the key
function list was independently confirmed nine times over by the baseline values
in the same session.

Two fields turned out to encode differently despite looking identical in the
interface:

* **Volume** stores the number you see, 0 to 31.
* **Backlight** stores one *less* than it shows, so display 1-7 is stored 0-6.

Either one guessed from the option list would have been wrong, and silently so.
That is the argument for measuring rather than inferring.

**Eleven of the 32 bytes are still unmapped** (+4 to +11, +17, +19, +21) and are
never written - the manufacturer's own software preserves most of them too. Nor
is any bit outside a named field ever touched. `noop_roundtrip.py` proves this:
writing every setting back at its current value moves zero bytes.

The rail has four tabs:

| Tab | Holds |
|---|---|
| **Channels** | three sub-tabs: Channel, Bulk edit, Checks |
| **FM radio** | broadcast presets and the FM VFO |
| **VFO A/B** | the two VFOs, one per band |
| **Radio settings** | radio-wide options, plus the read-only band limits |
| **Options** | transfer behaviour, then the serial traffic log |

Bulk edit opens with **Use the selected channel only** switched on. It acts on
whichever channel is highlighted in the table and names it beside the tick box,
so there is no doubt which one. The range boxes disappear, along with setting a
field across many channels and find-and-replace - for a single channel the side
panel and the table already do both, faster.

Turn the switch off and the full set appears: pick a range, set one field across
it, rename within it, then move, copy or delete. **Copy and move act on the channels that
exist**: an empty slot inside the range is skipped rather than written over the
destination, so copying 1-200 somewhere does not blank the target block.

**Hover anything for what it does.** Every field, button and toggle in the
channel editor, bulk edit, radio settings, FM and options carries an
explanation.

Encode and decode are **pickers**, not text boxes: all 260 valid values grouped
as CTCSS, DCS normal and DCS inverted, so a tone cannot be mistyped.

Radio settings are grouped as Radio, Display and sound, Transmit, Keys and
Security. **Each group folds away**, and only **Keys** is open to begin with - it is the one you come here to change. Which
groups you leave open is remembered on this computer.

The header runs file work on the left - **Open .icf**, **Save .icf**, **Tools**
- then the radio: the link lamp, **Connect**, **Read radio**, **Write radio**,
and the transfer meter.

**Open .icf** also takes `.img` from CHIRP and a raw `.bin`; the label names the
format you will use nine times in ten.

**Save .icf** writes `.icf` &mdash; channels, settings, FM, everything. It opens in
the manufacturer's software, in CHIRP, and back in here, so one format covers
every destination. There used to be a raw `.bin` alongside it; it held the same
11136 bytes without the text header, which is a conversion rather than a
different thing, and CHIRP could not identify it. If you ever want the raw
bytes, `th2000.py` writes them in one line.

**Tools** offers **Import channels (CSV)**, **Export channels (CSV)**, **Print
channel list**, and **Compare with…** last. The printed sheet carries channel,
name, receive, transmit, shift, encode, decode, power, bandwidth, step and scan
- eleven columns, none of which is ever blank, because a blank cell on paper
reads as missing data rather than as a default. The CSV entries say *channels*
because that is all a CSV holds &mdash; radio settings, FM presets and the intro
screen are not in one.

**About this tool** sits below the tabs rather than inside one, so the caveats
are reachable whichever tab you are on.

The panel starts at 500px, which is wide enough for the field grids to fall
into three columns, and will not be dragged below 400px - narrower than that
and the five tab names no longer fit on one line. The divider between it and the channel table can be
**dragged** to rebalance them. Double-click resets it; with the divider focused, the arrow keys
move it and Home resets. Below 1160px the layout stacks and the divider is
hidden. Below 620px the controls grow for touch, the field grids drop to one
column, and the table tightens up.

**Hover any setting for an explanation.** Scan type spells out what To, Co and
Se actually do; the squelch-tail option carries the manufacturer's full wording,
*Eliminate Squelch Tail When No CTC/DCS Signaling*; a label ending in * is
shortened, and hovering gives the full version.

**P5 long** shows as *Power Button*, disabled and marked fixed: that key
switches the radio on and off and the manufacturer's software will not reassign
it.

The **password** accepts digits only, matching the manufacturer's software.
Anything else is stripped as you type, and a short code is padded with zeros to
six.
Every control is a dropdown, including volume and backlight, so there is no
typing a number the field cannot hold. **Every key function explains itself.** The manufacturer's names - `KEY-M/V`,
`KEY-MONI`, `Talk Around` - are not self-evident, so each option in a P1-P5
dropdown carries a description, and the field itself says what the current
choice does. The labels are the manufacturer's; the explanations are the
standard meanings for this class of radio and are not individually confirmed on
a TH-2000. `KEY-Save` says so, because "Save" is used for both battery saving
and storing a frequency.

**P5 long** is read-only: that key is the
power button and the manufacturer's software will not reassign it.

Two rows appear only when they apply. The **intro screen lines** show once Intro
screen is set to *Char String*, and the **password box** once the boot-strap
password is switched on.

## Moving files between this and CHIRP

| From | To | Works |
|---|---|---|
| CHIRP `.icf` | this tool | yes |
| CHIRP `.img` | this tool | yes - the metadata CHIRP appends is ignored |
| this tool `.icf` | CHIRP | yes, opens directly |
| this tool `.bin` | CHIRP | no - CHIRP will not identify a raw image. Save `.icf` instead |
| CHIRP `.csv` | this tool | yes |
| this tool `.csv` | CHIRP | column names differ; CHIRP's generic CSV import will need the headers renamed |

**Prefer `.icf` for moving between the two.** It carries the whole codeplug,
settings included. CSV carries channels only, so radio settings, FM presets and
the intro screen are lost either way.

CHIRP's CSV uses its own spellings - `Location`, `Frequency`, `Mode` of FM or
NFM, `Skip` of S, and power as a wattage like `25W`. All of those are understood
on import; an unfamiliar wattage picks the nearest level this radio has.

## Working out what an unmapped byte does

Compare has a **byte level** section. For every byte that differs it shows the
address, which region it falls in, the value before and after in hex *and*
binary, and which bits moved:

```
addr    off  region                    before        after         bits
0x2020 +0   global settings           31 0011 0001  33 0011 0011  bit 1
0x2030 +16  global settings           00 0000 0000  E0 1110 0000  bits 5-7
```

Channel bytes are filtered out by default, because when channels differ they
drown everything else. They are one click away under *Include channel bytes*.

This turns mapping the settings block into a mechanical job:

1. Read the radio, save as `baseline.icf`.
2. In the manufacturer's software change **one** setting and save it.
3. Compare the two files here. The bits that moved are the answer.

The `+16` column is the offset within the 32-byte settings block, which is the
form worth writing down. There is a Copy button so the table can be pasted
straight into notes.

Nothing in the settings block is exposed as an editable control yet, and
deliberately so: a control for a field that was guessed rather than confirmed
is worse than no control at all.

## The transfer meter

The 22 segments are not decoration: there is one per 512-byte block, and the
last one is drawn narrower because the last block really is short (0x2B80 is
21 × 512 + 384). When a transfer stops you can see which block was in flight,
and hovering a segment gives its address. That matters more than a percentage
when something goes wrong mid-write.

## Tests

```bash
node th2000-core.test.js                    # no dependencies

npm install jsdom && node ui.test.js        # loads index.html for real
```

`ui.test.js` injects a fake `navigator.serial` backed by a radio simulator and
clicks the actual buttons. It covers connect, read, edit, write, verification,
`.icf` output, legacy framing, and the failure paths: a radio that never
answers, one that replies for the wrong address, one that silently corrupts a
block, and a browser with no Web Serial at all.

## What is verified, and what is not

Everything above passes: 193 core checks, 475 UI checks against both builds, 35
CHIRP driver tests, the 6-way no-op round trip, and the Python suite.

**None of it involves a physical radio.** The protocol was recovered by reading
the manufacturer's software, not by capturing a session. The simulator proves
the code agrees with my understanding of the protocol; it cannot prove that
understanding matches your radio. Read before you write, and keep that first
file.

Two specific things to check against hardware:

- **Inverted DCS polarity.** CHIRP's `th_uv88.py` places the decode and encode
  inversion bits the other way round from what this radio's own software does.
  I followed the software. If your inverted-DCS channels come out swapped, the
  two bits need exchanging.
- **Framing.** As above — if the handshake fails, try legacy.

## Two bugs the browser version found

Writing this turned up faults in the earlier deliverables, now fixed
everywhere:

1. **A zero tone slot rendered as `D000`**, which is not a real DCS code and
   could not be parsed back. Any channel with a zeroed tone word would have
   round-tripped into garbage. Fixed in the JS, the Python library and the
   CHIRP driver: zero means no tone, same as the `0x0FFF` sentinel.
2. **The CHIRP driver over-claimed DCS support.** It declared
   `ALL_DTCS_CODES`, which is the raw range 0–511. The radio's own table holds
   exactly the 104 standard codes, 023 to 754 — which is
   `chirp_common.DTCS_CODES`. Corrected.

A third fault came out of cross-checking the JS against the Python: the Python
library modelled the 6-byte in-record name and the 10-byte name table as two
separate fields, when they are one 16-character name. The CHIRP driver had this
right; the standalone library did not. Fixed.
